Read this before building anything Everything in this document assumes Better Impact genuinely has no retrievable history — which is confirmed true for every documented report and API endpoint, but not yet confirmed true for the underlying database. The discovery document now asks the admin directly: when a volunteer transitions Active → Inactive → Active, does Better Impact create a new record each time, or overwrite the same one? 01The core problem, stated precisely

If we only ever read Better Impact's current status, we can still answer start and end questions correctly (when did this person first appear as Active, when were they Archived) — those are single point-in-time facts and current-state reads capture them fine, eventually. What we lose is the middle: if a volunteer goes Active → Inactive → Active again, and we only check in periodically, we can miss the entire Inactive period if it falls between two of our checks.

02Gating risk: which plan BC SPCA is actually on decides whether Section 03 is even buildable

Confirmed from betterimpact.com/features — only the Impact plan includes the API Everything Section 03 proposes (a Fabric pipeline calling the Better Impact API on a schedule) requires API access, and the API is listed only under the top "Impact" tier — not Foundation, not Growth. BC SPCA's current tier is still unconfirmed (see the Integration Options document). Until that's known, treat the self-built-SCD2 fallback below as provisional, not a plan we can commit to.

If BC SPCA turns out to be on Foundation or Growth, and upgrading to Impact isn't approved, the automated path in Section 03 is not available at all — there is no API to call. The only remaining option becomes:

Manual-export-only pathSomeone at BC SPCA (the Better Impact admin, or whoever holds the granted access) has to manually log in, manually run the report, and manually send the export to the Data Team — on whatever cadence they're willing to repeat by hand, since Better Impact has no scheduling feature at any tier (confirmed in the Integration Options document). Any volunteer who went Inactive and back to Active in between two manual exports is invisible to us, and there is no tier-independent way to close that gap. This is a resourcing/cost decision for the Data Owner, not a technical workaround we can engineer around.

03The proposed fallback: build our own SCD2 from periodic snapshots

Since we already run our own pipeline into Microsoft Fabric for ShelterBuddy (the existing kennel_history_scd2 pattern), the same architecture applies here: call the Better Impact API on a recurring schedule, compare each pull against the last one, and insert a new history row only when something changed.

Step 1 — Scheduled pullFabric pipeline calls the Better Impact API (requires Impact-tier access — see the Integration Options document) on a fixed cadence. Each pull returns current status + last-change date for every volunteer.
Step 2 — Diff against the prior pullCompare each volunteer's status to what we stored last time. If unchanged, do nothing. If changed, close out the previous SCD2 row (set its end date) and open a new one with the new status, starting at the pull's own timestamp — not at Better Impact's last_status_change date, which may predate our detection of it.
Step 3 — Our own history tableOver time, this builds a Foster_Volunteer_Status_History table in the same shape as kennel_history_scd2 — but entirely self-collected, starting from zero the day we turn this on.

04Risk — granularity is capped by pull frequency, and a missed cycle is gone forever

This is exactly the scenario you described: if a volunteer goes Inactive and back to Active between two scheduled pulls, our pipeline never sees the Inactive state at all — by the time we check again, they're already back to Active, indistinguishable from someone who was never inactive.

05Risk — no retroactive backfill, unlike ShelterBuddy

This is the bigger risk, not the pull-frequency one ShelterBuddy's kennel_history_scd2 already has roughly 20 years of real history behind it. A self-built Better Impact SCD2 has none — it only starts accumulating from the day the pipeline is turned on, because there is nothing to backfill from; Better Impact itself never kept the earlier states either. The two history tables will look structurally identical but have wildly different depth.

Concrete consequence: the proposed 12-Month Repeat Retention % and 365-day Effective Behavioral Attrition signals (from the Foster Volunteer KPI research brief) both need roughly a year of history to compute meaningfully. If this fallback is built, those two signals will be data-starved for the first ~12 months after go-live — not broken, just not yet meaningful, since there's no prior year to compare against. The other three proposed signals (Utilization %, 1st-to-2nd Placement Conversion %, Shelter Days Saved) are less affected since they lean more on ShelterBuddy's own `AnimalID`+`PersonID` history, which already has depth.

06What would eliminate these risks

If the admin confirms Better Impact's database creates a new record on every status transition (Section 01's question), ask a direct follow-up: can Better Impact support staff run a one-time historical extract from the underlying database, even if no self-service report exposes it? That single confirmation could replace this entire fallback plan with real, deep history instead of a shallow one we have to grow ourselves.

07Decision this document does not make

Whether to actually build this fallback — and at what pull cadence — is a build-vs-wait call for the Data Owner/decision owner once the admin's answers are in, not something to decide from this document alone. This document only makes the tradeoff visible.
