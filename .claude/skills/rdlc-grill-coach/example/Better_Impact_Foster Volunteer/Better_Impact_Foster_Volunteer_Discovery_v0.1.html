Confirmed from Better Impact's own documentation Status changes are entirely manual — "the status of volunteers can only be changed by an administrator, and it must be changed manually" (one at a time or in bulk). There is no automatic trigger tied to actual volunteer activity. This independently confirms the core problem already identified in Lindsay's research brief: Active/Archived status reflects when an admin got around to updating a profile, not when a volunteer actually started or stopped fostering.

02A gap found during research — flag for the admin, not yet resolved

"Assign" is not a native Better Impact status. The lifecycle above has no step corresponding to "this volunteer is currently fostering this animal." That linkage — which volunteer has which animal — lives in ShelterBuddy, via the AnimalID+PersonID placement record, not in Better Impact. This matters for the KPI design: Better Impact can tell us who is nominally Active; it cannot by itself tell us who is actually doing anything right now. Worth confirming with the admin whether Better Impact's configured account has any scheduling/assignment feature in use that comes closer to this, or whether assignment truly only exists on the ShelterBuddy side.

04Questions for the Better Impact admin

Configuration — does BC SPCA actually use the standard model?
  1. Does BC SPCA's account use the standard 5 statuses (Applicant, In Process, Active, Inactive, Archived) as-is, or are any relabeled/customized? Is "member" the term BC SPCA actually uses, or does Better Impact only expose these 5 statuses under "volunteer" terminology? The research above is generic Better Impact documentation, not BC SPCA's actual setup.
  2. When a volunteer transitions Active → Inactive → Active again, does Better Impact create a new record/row each time, or does it overwrite the status field on the same existing record in place? This is the single most important question in this document. The published API and reports only expose current status + last-change date (confirmed, see Section 04 below) — but that doesn't prove the underlying database never kept the earlier rows. If status changes create new records, the history may genuinely exist in Better Impact's database even though no documented report or API endpoint surfaces it — worth asking the admin directly rather than concluding "no history exists" from documentation alone.
  3. Is "foster volunteer" tracked as its own distinct volunteer type/role/position within Better Impact, separate from BC SPCA's other volunteer programs (retail, dog walking, events, etc.), or is it mixed in with everyone else? If foster isn't cleanly separable in Better Impact itself, every downstream KPI needs a filter defined here, not invented later.
  4. Are there any custom fields or sub-statuses specific to foster volunteers (e.g., species they foster, capacity/availability, special training)?
  5. Confirmed from Better Impact's own documentation, worth verifying BC SPCA's specific setup: does BC SPCA have an "Activity" configured (e.g., "Foster Care") that volunteers log hours against? Better Impact has no native animal-identity field anywhere — any "which animal" link would be a manually-typed custom field, not a structured one. We are not proposing to use this as a replacement for ShelterBuddy's AnimalID+PersonID placement record (that stays the primary source for KPIs 4–5 in the discovery definitions document, since it's an operational system of record, not self-reported logging) — but a large gap between what ShelterBuddy shows and what's logged here would itself be a useful data-quality/engagement signal worth knowing about. Confirms there's no simpler, Better-Impact-only path for KPIs 4–5 that would avoid the ShelterBuddy join — and flags a possible secondary cross-check if such an Activity exists.
Real-world usage — is the status actually kept current?
  1. In practice, how promptly is a volunteer moved from Active to Inactive or Archived once they stop fostering? Is this done per-volunteer or in periodic bulk cleanups? Directly tests Lindsay's "ghost volunteer" and "lagging administrative spikes" concerns against real practice, not just general Better Impact documentation.
  2. Is Inactive actually used as a distinct, meaningful status at BC SPCA, or do volunteers mostly go straight from Active to Archived in practice? If Inactive isn't really used, the Retention/Attrition KPI should be designed around Active vs. Archived only, not a 3-state model that doesn't reflect real behavior.
  3. Who has authority to change a volunteer's status, and is there any written SOP for when it should happen?
Joinability — can we link Better Impact to ShelterBuddy at all?
  1. Is there any field in Better Impact that could serve as a join key to ShelterBuddy's PersonID (e.g., email, a BC SPCA staff/volunteer ID, name matching)? Without a reliable join key, none of the AnimalID+PersonID-anchored KPIs already proposed (Utilization %, Conversion %, Repeat Retention %, Behavioral Attrition, Shelter Days Saved) can actually be built.
  2. Is that join key unique and stable over time (not reused, not changed on re-application)?
  3. How far back does BC SPCA's actual Better Impact data go? Was there a system migration or start date, or does it cover the organization's full history? This directly limits a proposed historical roster-size approximation (see Foster_Volunteer_Discovery_KPI_Definitions_v0.1.html, KPI 9) intended to pair with the existing 20-year Animals-in-Foster trend — the approximation can only go back as far as real records exist.
Access and extract
  1. Confirmed directly from the published API payload, not inferred: Better Impact only tracks current status plus the date of the last status change — not a history of earlier changes. The API's volunteer status fields are exactly volunteer_status (current), volunteer_inactive_status_reason/volunteer_archived_status_reason (current reason), and volunteer_last_status_change (a single date) — no status-history array, no audit-log endpoint, anywhere in the documented payload. The Personal Profile Raw Data report's Status Fields match this exactly. If a volunteer goes Active → Inactive → Active again, nothing in Better Impact shows that middle Inactive period once they're back to Active. Confirms a point-in-time export can't support any time-based analysis of Better Impact's own status field. Not a blocker for the proposed KPIs, which are ShelterBuddy-anchored instead — but worth the admin knowing this is a known system limitation, not a configuration gap on BC SPCA's end. Suggested email to Better Impact, since this now informs a real architecture decision: confirm no status history exists anywhere, even on higher account tiers, rather than just in the public docs.
  2. Given that limitation, would BC SPCA consider a periodic snapshot export (e.g. weekly pull of current status per volunteer, saved to Fabric) to reconstruct status history going forward, the same way a Type-2 history table is built from any source that only exposes current state? This only matters if BC SPCA later wants historical analysis of Better Impact's own Active/Archived status itself (Layer 1, admin hygiene) — not required for the ShelterBuddy-anchored Layer 2 signals.
  3. What export/API options exist, and at what refresh frequency?
