1. The real problem: a report request is not a data-product request

When a Data Owner asks for "a report," what they're actually describing — without knowing it — is a data product they don't know how to specify. Most project failures don't come from the build being technically wrong. They come from building the report anyway, without ever building the product underneath it.

A report

A one-off visualization of whatever gets built. It looks finished the moment it renders. Nothing underneath it says whether the number is right, what it means when an edge case hits, or who's allowed to change its definition.

A data product

The governed foundation underneath the report: a confirmed definition, a validated grain and population, known edge cases, a named owner. The report becomes one of possibly many things built safely on top of it.

This is the real, unedited starting point for the worked example in this document:

"Some potential definitions that we can work on with Lindsay:

Retention = # of fosters that stay (i.e. remain active) with BC SPCA >1 yr
Attrition = # fosters lost (i.e. # archived) every year/quarter/etc" — Maggie Stewart, Teams message, on behalf of Lindsay (Foster Volunteer Member Support)

Taken literally, this is enough to build a report in an afternoon — a number that moves on a chart. It is not enough to build the product underneath it: which field "active" actually reads from, whether a volunteer who leaves and comes back is counted once or twice, what decision the number is meant to support, what "every year/quarter/etc" should default to when nobody's chosen yet. None of that surfaces when you build the report. All of it surfaces when you build the product — which is exactly what the chain in this document exists to do before a single visual gets built.

2. This is human-in-the-loop AI, not agentic AI

Worth stating plainly, not just implying through the gates described later: this engine is not agentic AI. An agentic AI pursues a goal on its own — it chooses its own steps, takes action, and moves forward with little or no per-step human confirmation. That is explicitly ruled out here.

Not this — agentic AI

AI is given a goal ("build the report") and decides the steps, the definitions, and when it's done, with the human reviewing only the end result — if at all.

This — human-in-the-loop AI

AI drafts exactly one document, from one fixed template, at a time. Nothing moves to the next stage until a named human — the Data Owner, the decision owner, the developer — explicitly confirms it. The AI never decides what's true, what's in scope, or what's finished.

Two rules hold this in place at every single stage, with no exception written into this process anywhere: No Decision → No Artifact. No Confirmation → No Action. AI accelerates the drafting. It does not replace the decision.

3. The engine: how the layers fit together

Legacy systems are good at recording transactions, not at producing decision-ready numbers. The engine's job is the layer in between: turn what the source systems hold into standardized, governed data a report can actually use — with a human confirming each layer before the next is built on top of it.

Build from the bottom up: a mock-up or an AI-suggested insight only works when the governed layers under it — the KPI contract, the confirmed grain, the sign-off — are already in place. Skipping a layer to go faster is exactly what produces a wrong number nobody catches until it's too late.

Every row above produces a draft. None of them is a decision. The KPI's formula, the project's scope, what's deferred, and whether the result is "confirmed" are calls only the Data Owner or decision owner makes.

5. The minimal document set

Not every project needs the full chain run at full depth. Three things are never optional, no matter how small the ask is. Everything else should scale with how ambiguous or risky the request actually is — not be produced by default just because a template exists.

Always requiredWhy it can't be skipped
Required KPI / Requirements RegisterThe one artifact that forces the real definition into the open — formula, population, grain. Skip this and you've built a report on an ask nobody actually agreed on.
Required Confirmed requirements (full BRD, or a lightweight Shared Understanding Summary for a small ask)The explicit sign-off moment. It can be short for a small project, but it cannot be silent — "ok sounds good" mid-chat is not confirmation.
Required Table Definitions (confirmed structure)The build will break on the first edge case without an agreed grain and relationship design — this is where a wrong assumption becomes expensive to unwind.
Scales with riskGo deep when…Safe to thin or skip when…
Scales Industry Standard ReferenceThe business language is contested or ambiguous (e.g. "Retention" means something different to three different people)The metric is simple and uncontested (e.g. a straightforward count already defined the same way everywhere)
Scales Source System DiscoveryThe source system is new or poorly understood (a first-time Better Impact extraction)The source system is already well-integrated and its fields are already trusted
Scales Technical Integration & RiskThere's real integration risk — an unreliable field, an unconfirmed API/export pathThe integration path is already proven; fold any residual risk into the BRD's Assumptions section instead of a standalone document
Scales Analysis Design + Mock ReportThe report needs real analytical depth — comparisons, driver discovery, multiple stakeholder viewsIt's a single, well-understood KPI tile with no diagnostic layer needed — a quick mock may be enough

The worked example in the next section went deep on every single one of these — because Better Impact was a genuinely new, poorly understood source system with real definitional ambiguity. That's a case for going deep, not the default minimum every project needs.

7. What this proved, and what's still open

In one continuous working session, the chain above took a two-line Teams message to a clickable, two-page mock report with real BC SPCA branding, a defined KPI set backed by a hand-validated worked example, and a named statistical method behind every proposed insight — without ever treating an unconfirmed upstream artifact as if it were settled. That is the actual claim being made: not that the report is finished, but that the path from raw ask to reviewable prototype is short, fast, and doesn't silently skip governance to get there.

What's still open, stated plainly rather than hidden: Lindsay has not yet confirmed the BRD or the KPI set; whether Better Impact's "Active date" and "Archived date" are real, reliable fields is unconfirmed; whether a volunteer can move from Archived back to Active, and whether any trace survives it, is unconfirmed; and the ShelterBuddy↔Better Impact join key itself is unconfirmed. None of these gaps were resolved by assumption — each is logged as an open question for the Data Owner or the system admin, exactly as the engine requires.

8. Why this matters, and what it actually encodes

  • Speed. One developer, directing AI through each stage, produced a full requirements chain and a working UX prototype in a single session — work that would traditionally need a BA, a data analyst, a UX designer, and a developer in sequence.
  • Governance. Every stage has a non-negotiable gate it will not skip without saying so out loud. Nothing gets labeled "confirmed" because it would be convenient to move on.
  • Repeatability, demonstrated now, not just claimed. The same RDLC OS skill set is active, right now, on several other initiatives in this repository — Centre & Animal Type Utilization (Draft for business review), SB Status & Source Pathway (Draft), the Self-Service Data Platform (In progress), the Triage Dashboard (Early). None of those is claimed complete here either — the point is that this isn't a one-off script written for Foster Volunteer specifically; it's the same pipeline, independently in motion, across different source systems and different Data Owners.
What this process actually encodes
Bridging a non-technical Data Owner's ask and a technical build has traditionally depended on one experienced person's judgment, call by call — knowing which question to ask, which ambiguity to chase down, which gate not to skip. Writing that judgment down as a fixed, gated sequence of document types means a developer who doesn't yet have that judgment can still run the same bridge safely — the gates catch what their own experience might not yet catch.

9. Getting started on your own initiative

Any future Data Owner request — in any system, not just Better Impact or ShelterBuddy — can enter this same chain. Concretely, for a developer picking this up:

  1. Read PROJECT_STATUS.md at the repository root — the index of every initiative already in flight, so a new ask doesn't collide with an existing name or KPI.
  2. Read the specific skill's own definition under .claude/skills/<skill-name>/SKILL.md before using it — each one states its own non-negotiable gate and required input.
  3. Start with rdlc-grill-coach on the raw ask, exactly as received — don't clean it up first. Use the Foster Volunteer Engagement example folder as a structural pattern only, never copy its specific content into a different ask.
  4. Use Section 5's minimal-document table to decide how deep to go — a simple, uncontested ask doesn't need the full ten-stage chain; a new, poorly understood source system does.
  5. Don't move to the next stage until the current one is explicitly confirmed by the Data Owner — not discussed, not "sounds good," confirmed.
