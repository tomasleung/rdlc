1. The problem: the raw ask

Most Data Owners don't know how to specify a data product. They aren't supposed to — that's not their job. What they send is something like this, exactly as it arrived for this project, over Teams:

"Some potential definitions that we can work on with Lindsay:

Retention = # of fosters that stay (i.e. remain active) with BC SPCA >1 yr
Attrition = # fosters lost (i.e. # archived) every year/quarter/etc" — Maggie Stewart, Teams message, on behalf of Lindsay (Foster Volunteer Member Support)

That's a real, usable starting point — but it is not yet a data product. It doesn't say which system field "active" actually means, whether a volunteer who leaves and comes back is counted once or twice, what decision this number is supposed to support, or what "every year/quarter/etc" should default to. Built literally, as received, it would produce a number — just not necessarily the right one, and nobody would find out until it was already in front of a manager.

Two ways this normally goes wrong: it gets built fast and literally, and breaks quietly later when an edge case (a reactivated volunteer, an unconfirmed field) surfaces; or it waits for someone to write a full specification nobody currently has time to produce. The RDLC OS engine is built to avoid both — a fixed, fast sequence that turns the raw ask into a governed spec without needing the Data Owner to already know what a governed spec looks like.

Build from the bottom up: a mock-up or an AI-suggested insight only works when the governed layers under it — the KPI contract, the confirmed grain, the sign-off — are already in place. Skipping a layer to go faster is exactly what produces a wrong number nobody catches until it's too late.

3. How AI scales the implementation

Each RDLC OS skill stands in for one specialist role on a traditional project team — drafting that role's output from a fixed template, never deciding on the Data Owner's behalf.

Every row above produces a draft. None of them is a decision. The KPI's formula, the project's scope, what's deferred, and whether the result is "confirmed" are calls only the Data Owner or decision owner makes — the engine's non-negotiable rule across every stage is No Decision → No Artifact, No Confirmation → No Action.

5. Proof point: Foster Volunteer Engagement, as built so far

In one continuous working session, the chain above took a two-line Teams message to a clickable, two-page mock report with real BC SPCA branding, a defined KPI set backed by a hand-validated worked example, and a named statistical method behind every proposed insight — without ever treating an unconfirmed upstream artifact as if it were settled. That is the actual claim being made: not that the report is finished, but that the path from raw ask to reviewable prototype is short, fast, and doesn't silently skip governance to get there.

What's still open, stated plainly rather than hidden: Lindsay has not yet confirmed the BRD or the KPI set; whether Better Impact's "Active date" and "Archived date" are real, reliable fields is unconfirmed; whether a volunteer can move from Archived back to Active, and whether any trace survives it, is unconfirmed; and the ShelterBuddy↔Better Impact join key itself is unconfirmed. None of these gaps were resolved by assumption — each is logged as an open question for the Data Owner or the system admin, exactly as the engine requires.

6. Why this matters

  • Speed. One developer, directing AI through each stage, produced a full requirements chain and a working UX prototype in a single session — work that would traditionally need a BA, a data analyst, a UX designer, and a developer in sequence.
  • Governance. Every stage has a non-negotiable gate it will not skip without saying so out loud. Nothing gets labeled "confirmed" because it would be convenient to move on.
  • Repeatability, demonstrated now, not just claimed. The same RDLC OS skill set is active, right now, on several other initiatives in this same repository — Centre & Animal Type Utilization (Draft for business review), SB Status & Source Pathway (Draft), the Self-Service Data Platform (In progress), and the Triage Dashboard (Early). None of those are claimed complete here either — the point is that this isn't a one-off script written for Foster Volunteer specifically; it's the same pipeline, independently in motion, across different source systems and different Data Owners.

7. What AI does not decide

The engine's credibility depends on this section being true, not just stated. Concretely, in this one initiative:

  • When the KPI design implied a volunteer's status history might be silently overwritten on reactivation (an SCD1-style risk), that was flagged back to the Data Owner as an open question — not assumed away so the KPI could ship clean.
  • The Analysis Design and Mock Report were built only as explicitly-labeled drafts/previews, because the BRD they depend on isn't confirmed yet — the engine did not quietly treat "good enough to look at" as "confirmed."
  • Every status pill color and threshold in the mock report is marked illustrative, because no benchmark has actually been approved — the engine did not default to a generic green/yellow/red scorecard just because that's the common convention.

The rule underneath all three: No Decision → No Artifact. No Confirmation → No Action. AI drafts every document in the chain; a named human decides what's true, what's in scope, and when something is actually done.

8. What this enables going forward

Any future Data Owner request — in any system, not just Better Impact or ShelterBuddy — can enter this same ten-stage chain. The document types don't change; only their content does. A single developer, using AI to draft each stage under the Data Owner's sign-off, can move from "here's roughly what I want" to a reviewable prototype fast enough to get real reaction before investing in a real build. This document is the write-up of that engine; Foster Volunteer Engagement is simply the first complete run of it captured end to end.
