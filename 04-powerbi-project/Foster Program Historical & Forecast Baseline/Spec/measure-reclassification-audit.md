## Methodology

1. Read `Spec\semantic_model_measure_standard.md` in full for the classification rules (Domain KPI / Base Measure / UI Formatting / Dynamic Title-Text) and the `_Formatting & Display` subfolder convention.
2. Read `KPI.tmdl` in full (3,476 lines, 157 measures) and extracted every measure's name, `displayFolder`, DAX body, `formatString`, and whether it carries a `///` doc-comment.
3. Built a **dependency map** by regex-scanning each measure's own DAX body for `[Measure Name]` bracket references that match another measure's exact name (column references like `'Date'[Year]` are excluded because they're immediately preceded by a closing quote).
4. Parsed every `visual.json` across all 3 pages, **removing the `filterConfig` subtree before scanning** (per the user's explicit scope rule — filter-only references do not count as "used by a visual"), then extracted every remaining `"Measure": { "Expression": {...}, "Property": "<name>" }` reference — this covers field-well projections, textbox dynamic-text bindings (`values[].properties.expr`), and conditional-formatting bindings (fill/font/background color rules) uniformly, since PBIR encodes all of them the same way.
5. Computed **Status** via transitive closure: a measure is "Used directly by a visual" if it appears in some visual's non-filter measure set; "Dependency only" if it isn't used directly but is reachable by walking backward through the DAX-reference graph from some measure that IS used (directly or transitively); otherwise "Unused."
6. Classified every measure as **Domain KPI** / **UI Formatting** / **Dynamic Title/Text** using the standard's output-type decision rule: numeric output → Domain KPI; string output that is a hex/RGB color → UI Formatting; any other string output (narrative, label, status badge text, categorical name) → Dynamic Title/Text. Name-suffix matches (`...Color`, `...Label`, `...Headline`, `...Description`, `...Insight`/`...Insighn`, `...Conclusion`, `...Narrative`, `...Subheadline`, `...Annotation`) were marked **high** confidence; measures classified purely by inspecting the DAX `RETURN` shape (bare string literal, `SWITCH` returning text, string concatenation) with no such name cue were marked **medium** confidence.
7. Proposed a new folder and `IsHidden` value per the standard's placement rules (see Notes for the folder-naming convention used and the specific judgment calls applied).

## Notes, Caveats, and Judgment Calls

**Dependency detection is regex/text-based, not a real DAX parser.** The dependency map is built by scanning each measure's DAX body for `[Measure Name]`-shaped bracket tokens that exactly match another measure's name, excluding tokens immediately preceded by a closing quote (`'Table'[Column]` column references). This will miss or misattribute dependencies that go through:
- `SELECTEDMEASURE()` / calculation groups (none exist in this model today, but if added later this method won't see through them).
- String-built or indirectly-referenced DAX (e.g., a measure name assembled via `SWITCH`/variable indirection rather than a literal `[Name]` token).
- It correctly ignores local variable names and `ADDCOLUMNS`/`SUMMARIZE`/`GENERATESERIES`-created column aliases (e.g., `[Value]`, `[AnimalCount]`, `[MonthlyValue]`) because those never coincide with an actual measure name — but a future measure or column that happens to share a name with one of these local aliases could produce a false positive.

**`filterConfig` exclusion rule, applied exactly as specified.** Three measures — `Completed Year Filter`, `Recent Years Filter`, `Forecast Validation Filter` — are referenced *exclusively* inside `filterConfig` blocks on four visuals (Fostered Animals Trend Chart, Intake Animals Trend Chart, Recent Fostered Animals Column Chart, Forecast Validation Table), each as a visual-level filter condition (`= 1`) that trims the chart's year axis. Per the user's explicit instruction, filterConfig-only references do not count toward "used by a visual," so all three measures show as **Unused** in this audit even though they are functionally load-bearing filter plumbing for those four visuals. This is a known, deliberate consequence of the scope rule, not an oversight — flagged here so the human reviewer doesn't delete these three measures outright when cleaning up "unused" measures.

**"Filter helper" measures don't cleanly fit the three classification categories.** `Completed Year Filter`, `Recent Years Filter`, and `Forecast Validation Filter` all return a bare `0`/`1` numeric flag used only as a visual-filter condition — they're not "Base Measure" raw aggregations (no `SUM`/`COUNT` on a column) and they're not decision-grade Domain KPIs either (nobody reads "1" off a card). They were classified **Domain KPI** by elimination (numeric output, so neither UI Formatting nor Dynamic Title/Text apply) at **medium** confidence. The human may want to introduce a fourth informal bucket (e.g., "Filter Helper") for these three in the eventual folder reorg, or simply leave them in their current domain folders and hide them (proposed here) since nothing should ever need to pick them from the field list directly.

**String-output measures with no name-suffix cue were classified by DAX return shape (medium confidence).** `Current Era Name`, `Largest Era Name`, `Lowest Month`, `Peak Month`, `Current Year Lowest Month`, `Current Year Peak Month`, `Peak Season Start Month`, `Peak Season End Month`, `Planning Priority`, `Monthly Performance Status`, `Program Status`, `Forecast Status`, and `YTD Performance Status` all return plain strings (a month name, an era name, a priority tier, or a status-badge phrase) with no `Label`/`Headline`/`Insight`/etc. suffix to key off. Per the standard's binary numeric/string decision rule, string output that isn't a hex color falls into Dynamic Title/Text by elimination — but several of these (the month/era/priority "name" measures in particular) are really categorical **data values** standing in for what would otherwise be a dimension attribute, not narrative text. They're flagged here as the audit's lowest-confidence judgment calls; a human may reasonably decide some of these should stay visible in a "Domain KPI"-like root position (e.g., `Peak Month`, `Lowest Month` are read directly off KPI tiles as factual answers, not prose) even though this audit defaults them to Dynamic Title/Text with `IsHidden = false` (which keeps them visible in the field list either way — the practical effect of the folder question is where they sit, not whether a user can find them).

**`Report Title`'s proposed folder is a judgment-call exception.** Its current folder is `Capacity & Support\Titles` — a one-measure, already-display-oriented folder that isn't itself a business sub-domain. Rather than propose `Capacity & Support\Titles\_Formatting & Display` (double-nesting a folder that exists only to hold this one dynamic-text measure), this audit proposes folding it directly into `Capacity & Support\_Formatting & Display`. A human may instead prefer to just rename `Titles` to `_Formatting & Display` in place — either way, the `Titles` folder should probably not survive as its own thing once the standard folder convention is adopted.

**No measure is missing a `displayFolder`.** Every one of the 157 measures in `KPI.tmdl` has a non-empty `displayFolder`, so there are no "needs a human decision because it has no folder at all" cases this time.

**Measures with no `formatString` were still classified Domain KPI when numeric.** Several Domain KPI measures (e.g., `5-Year Benchmark Monthly Label` — no, that one's text; but e.g. `Prior Year Same Month Variance %`, `Average Monthly Benchmark`, `Planning Outlook Low/High/Midpoint/Series`, `Forecast Outlook Value`) have no explicit `formatString` but carry a `PBI_FormatHint = {"isGeneralNumber":true}` annotation confirming numeric output — these were classified Domain KPI with high confidence on that basis, not left ambiguous.

**No "Base Measure" category measures exist.** `Fostered Animals` (`DISTINCTCOUNT('Foster Animal Month'[SB Animal ID])`) and `Intake Animal` (`DISTINCTCOUNT('Intake'[AnimalId])`) are the only single-line raw-aggregation measures in the model, but both are explicitly documented as the model's primary headline KPIs and both are directly visualized on "Foster Program Summary" — they stay Domain KPI, not Base Measure, consistent with the prior reorg plan's own conclusion.

**`IsHidden` proposals for "Dependency only" and "Unused" Domain KPI measures extend the task's rule by judgment, as instructed.** The rule as given only explicitly calls for hiding "Dependency only" Domain KPI measures with no visual binding of their own. This audit additionally proposes hiding genuinely **Unused** Domain KPI measures (not even a dependency of anything) on the reasoning that if nothing — not a visual, not another measure — needs them, they're even stronger candidates for hiding than dependency-only ones. This is explicitly a suggestion, not a hard rule; a human may prefer to leave truly unused measures visible (as a visible invitation to either wire them up or delete them) rather than hide them. The 52 "Unused" measures in this table are also worth a separate conversation about outright deletion versus hiding — this audit only answers the hide/show question per the task's scope, not the keep/delete question.

**Measures with multiple visuals/pages are listed in full, not truncated.** `Fostered Animals` in particular is referenced by 44 other measures' DAX (it's the model's foundational metric) — its "Used By Other Measures" cell is intentionally long rather than abbreviated, since completeness was prioritized per the task's instructions.
