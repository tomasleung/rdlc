# Change-Point Detection and Outlier/Anomaly Detection for Monthly Seasonal Count Data (BI/DAX context)

## What is the correct formula/procedure for CUSUM, and is it realistically implementable as a running DAX measure, or does it need external tooling?

### Takeaway
CUSUM (cumulative sum control chart) is a simple two-sided running-sum recursion originally designed for hand/paper calculation, so its *math* is well within DAX's reach as a running-total pattern over an ordered date index; the real barrier for a BI analyst is not the formula but choosing defensible parameters (target mean, k, h) and building a correct recursive running-sum in DAX, which has no native recursion function and needs an iterator/variable-table workaround — doable, but non-trivial, and brittle if visual-level filters change the "ordered sequence."

### Cited Findings
- The tabular (two-sided) CUSUM keeps two running sums from standardized observations z_t: Upper S_t⁺ = max(0, S_(t−1)⁺ + z_t − k); Lower S_t⁻ = max(0, S_(t−1)⁻ − z_t − k); both start at zero, and a shift is signaled when S_t exceeds a decision threshold h — [CUSUM — Wikipedia](https://en.wikipedia.org/wiki/CUSUM); corroborated by [SAS QC: XCHART CUSUM Procedure](https://support.sas.com/documentation/cdl/en/qcug/68161/HTML/default/qcug_cusum_sect024.htm)
- In standardized-sigma units, parameters are commonly written K = kσ and H = hσ; default values k = 0.5 and h = 5 give an in-control Average Run Length (ARL) of roughly 465 — [Six Sigma Study Guide, CUSUM chart](https://sixsigmastudyguide.com/cusum-chart/)
- CUSUM's advantage over a simple Shewhart (3-sigma) chart is greater sensitivity to small, sustained mean shifts rather than single large spikes — [CUSUM — Wikipedia](https://en.wikipedia.org/wiki/CUSUM)
- The original method is E. S. Page, "Continuous Inspection Schemes," *Biometrika* 41(1–2), pp. 100–115, 1954 (DOI 10.1093/biomet/41.1-2.100; JSTOR 2333009) — [CUSUM — Wikipedia](https://en.wikipedia.org/wiki/CUSUM); title spelling and exact month vary slightly across mirrors, flagged below.
- Power BI/DAX guidance confirms the general running-total pattern (CALCULATE + FILTER with ALL on the date column and a MAX(date) boundary, or the newer WINDOW function in recent Power BI versions) as the standard way to build a cumulative measure, and warns that incorrect filter-context handling produces totals that look right in the aggregate but are wrong at the row level — [EPC Group, Power BI Running Total DAX Guide](https://www.epcgroup.net/blog/power-bi-running-total-cumulative-sum-dax-guide-2026); [The Bricks, Running Total in Power BI](https://www.thebricks.com/resources/guide-what-is-running-total-in-power-bi)
- No source was found describing a published, ready-made CUSUM-specific DAX pattern (i.e., nobody has written up the max(0, …) recursion as a canonical Power BI recipe); this is an acknowledged gap, not a confirmed non-feasibility.

### Inferences
- Because CUSUM's recursion is "previous period's running sum + this period's deviation, floored at zero," it is structurally the same shape as a running total with a floor and a reference-value offset — a BI analyst who already knows the running-total DAX pattern (iterate chronologically, accumulate) can adapt it, provided the model has a true unbroken monthly date index (no gaps) since the recursion depends on strict period-over-period order.
- The real design burden is upstream of DAX: picking a sensible "target" (in-control mean) and k (how large a sustained shift to care about) for count data with known seasonality requires first removing the seasonal component (e.g., comparing to a seasonal baseline or using year-over-year ratios) — a raw monthly count fed straight into CUSUM would trigger false "shifts" purely from the June–October seasonal swing. This is an inference about combining Part A and Part B methods, not a sourced claim.
- Given the DAX recursion complexity (two running sums, floor operations, parameter tuning) and the lack of an off-the-shelf pattern, a "Must"-tier BI skill should likely specify CUSUM only as a simplified/approximate version (e.g., signed running sum of seasonally-adjusted deviations divided by a baseline sigma, flagged when it crosses a fixed threshold like ±4), not the textbook two-sided recursion with tuned k/h — that fuller version is better flagged as a "Prefer, with analyst/stats support" or exported-to-R/Python item.

### Gaps
- No primary source gives a worked example of CUSUM implemented natively in DAX/Power BI; this had to be inferred from general running-total DAX patterns plus the CUSUM formula from control-chart literature.
- No source quantifies how much seasonal count data (vs. roughly constant-mean process data, which is what CUSUM/SPC was designed for) degrades CUSUM's false-alarm rate without seasonal pre-adjustment.
- Minor citation inconsistency: Wikipedia mirrors differ on Page's exact 1954 article title ("Continuous Inspection Schemes" vs. "Continuous Inspection Scheme") and month; not resolved against the Biometrika original in this research pass.

## What is PELT, at a conceptual level a BI analyst could understand, and is it accessible without Python/R?

### Takeaway
PELT (Pruned Exact Linear Time) is an *offline, multiple*-change-point method that finds the statistically best way to cut a whole series into segments, each with its own mean/variance, by minimizing a penalized cost function — conceptually "automatically find all the breakpoints that best explain the whole 20-year history at once," which is a fundamentally batch/optimization operation with no equivalent in DAX; it requires the R `changepoint` package or Python `ruptures`/`sktime`/`skchange`, run outside Power BI (or inside an R/Python visual or Power Query script step), making it squarely a "needs specialist tooling" item for a self-service BI skill.

### Cited Findings
- PELT was introduced in Killick, Fearnhead & Eckley, "Optimal detection of changepoints with a linear computational cost," *Journal of the American Statistical Association* 107(500), pp. 1590–1598, 2012 — [arxiv-vanity preprint](https://www.arxiv-vanity.com/papers/1101.1438/); [changepoint R package reference, JSS](https://www.jstatsoft.org/article/view/v058i03)
- PELT solves a penalized optimal-partitioning problem (find the segmentation of the series that minimizes total within-segment cost plus a penalty per added changepoint), using a pruning step over the set of admissible previous changepoint locations to cut computation — [JSS, changepoint R package](https://www.jstatsoft.org/article/view/v058i03)
- The authors report PELT can be orders of magnitude faster than other exact segmentation methods, and that its exactness improves segmentation accuracy versus Binary Segmentation (a simpler, greedy, sequential-split alternative) — [arxiv-vanity preprint](https://www.arxiv-vanity.com/papers/1101.1438/)
- PELT's output still depends on a user- or algorithm-chosen penalty value; follow-up work (Haynes, Fearnhead & Eckley) introduced CROPS to explore many penalty values at once rather than requiring one fixed guess — [arxiv-vanity preprint](https://www.arxiv-vanity.com/papers/1101.1438/)
- Implementations exist in R (`changepoint` package by Killick & Eckley) and Python (`ruptures`, `sktime`, `skchange`) — [JSS, changepoint R package](https://www.jstatsoft.org/article/view/v058i03); [skchange PELT docs](https://skchange.readthedocs.io/en/stable/api_reference/auto_generated/skchange.change_detectors.PELT.html)
- Power BI supports R- and Python-powered custom visuals and Power Query "Run R/Python script" steps, but this requires a local R/Python installation with the needed packages, and for the Power BI Service, viewers need R/Python available (directly or via gateway) to render R/Python visuals — [Microsoft Learn, R-powered custom visuals](https://learn.microsoft.com/en-in/power-bi/create-reports/desktop-r-powered-custom-visuals); [Microsoft Learn, Create custom visuals with R or Python](https://learn.microsoft.com/en-us/training/modules/understand-advanced-data-visualization-concepts/5-create-custom-visuals)
- Power BI Service script visuals have moved to Python 3.11 / R 4.3.3 runtimes, and Microsoft warns that upgrades can break existing R/Python visuals that depend on older package versions — [Power BI blog, update to R/Py visuals](https://powerbi.microsoft.com/en-us/blog/important-update-coming-to-r-py-visuals-in-power-bi/)
- No source was found confirming a native Power BI/AppSource marketplace custom visual that implements PELT or general changepoint detection out of the box; this remains unconfirmed/unverified.

### Inferences
- PELT is fundamentally a global-optimization algorithm over the *entire* series (it looks backward and forward, revisiting candidate segmentations), which has no analog in DAX's row-by-row/filter-context evaluation model — there is no legitimate "manual approximation" of PELT itself in a spreadsheet beyond informally eyeballing a chart for level shifts, which is not actually PELT.
- Given the setup cost (installing R/Python, maintaining package versions, and the Power BI Service rendering dependency), PELT should be classified as clearly out of scope for a "Must"-tier self-service BI deliverable, and only usable as a one-off specialist (data scientist) analysis feeding *static* results back into the BI model (e.g., a pre-computed "detected changepoint date" column loaded via Power Query after an offline R/Python run) rather than a live, interactive DAX measure.

### Gaps
- No confirmed example of a maintained Power BI custom visual dedicated to changepoint/PELT detection was found in this search pass — flagging as unresolved rather than asserting none exists.
- No source discusses PELT's practical runtime/complexity specifically at the ~240-month (n=240) scale relevant here; given PELT's near-linear cost claim, performance is very likely a non-issue at this small n, but this was not explicitly confirmed by a source for n≈240.

## What's the simplest legitimate approximation of change-point detection a governed BI skill could specify as "Must" vs what requires flagging as "needs a data scientist"?

### Takeaway
A defensible "Must"-tier approximation is a seasonally-adjusted control-chart signal — i.e., compute each month's deviation from a seasonal baseline (same-month multi-year average), standardize it, and apply simple, well-documented SPC decision rules (Western Electric / Nelson rules: e.g., one point beyond 3σ, or 8 consecutive points on one side of the baseline) as the "flag for investigation" trigger; full CUSUM with tuned parameters, Bayesian change-point detection (BOCPD), and PELT should be tiered as "Prefer only with specialist support" or "Avoid in self-service DAX," because they require either recursive state not natively supported in DAX, posterior/probabilistic computation, or whole-series batch optimization.

### Cited Findings
- The Western Electric rules (1956) define four classic out-of-control signals: one point beyond 3σ; 2 of 3 consecutive points beyond 2σ (same side); 4 of 5 consecutive points beyond 1σ (same side); 8 consecutive points on one side of the centerline — [QualityGurus, Nelson Rules (and Western Electric Rules)](https://www.qualitygurus.com/nelson-rules-and-western-electric-rules-for-control-charts/)
- Lloyd Nelson's 1984 rules (eight total) retain the Western Electric tests and add rules for trend (6 monotonically increasing/decreasing points), oscillation (14 alternating points), stratification (15 points within 1σ, suggesting understated variance), and mixture (8 points beyond 1σ split across both sides) — [QualityGurus, Nelson Rules](https://www.qualitygurus.com/nelson-rules-and-western-electric-rules-for-control-charts/); implemented in software, e.g. MATLAB's `controlrules` function — [MathWorks, Control Chart Rules](https://www.mathworks.com/help/stats/controlrules.html)
- Sources disagree on minor threshold details (e.g., one vendor's "same side" rule uses 9 points, another 8) — flagged explicitly as a cross-source discrepancy; verify the exact count against a primary SPC reference before hard-coding thresholds — [QualityGurus](https://www.qualitygurus.com/nelson-rules-and-western-electric-rules-for-control-charts/); [Parsec Corp, Nelson vs Western Electric](https://parsec-corp.com/nelson1)
- A control-chart rule violation is explicitly framed in the SPC literature as a signal to investigate an "assignable cause," not proof that one exists — "a rule violation suggests an assignable cause — it does not prove one exists" — [QualityGurus](https://www.qualitygurus.com/nelson-rules-and-western-electric-rules-for-control-charts/)
- Bayesian Online Changepoint Detection (BOCPD) traces to Adams & MacKay (2007) and returns a *probability* of a changepoint at each time point plus credible intervals, rather than a single binary flag — [Knogin, Bayesian changepoint detection](https://knogin.com/en/developers/bayesian-changepoint-detection)
- The Chow test (Chow, 1960) tests whether regression coefficients differ before/after a *pre-specified* break date; it requires running three OLS regressions (full sample, pre-break, post-break) and computing F = ((RSS_R − RSS_U)/k) / (RSS_U/(n − 2k)); it needs a known candidate break date (if the date itself is unknown, a sup-F test is the appropriate alternative, which is more specialist territory) — [Panelbox, Chow Test reference](https://panelbox.readthedocs.io/en/latest/diagnostics/specification/chow/); [MetricGate, Chow Test calculator methodology](https://metricgate.com/calculator/chow-test)
- The Chow test's residual sums of squares can be obtained in Excel via LINEST or the Analysis ToolPak regression tool, with the F-statistic compared against F.INV.RT — i.e., Chow is realistically spreadsheet-feasible, but only when the analyst already has a specific candidate break date in mind (e.g., "did foster placements shift after the March 2023 policy change?") rather than being used to discover an unknown break date — [MetricGate, Chow Test methodology summary](https://metricgate.com/calculator/chow-test)

### Inferences
- A practical tiering for a governed BI skill: **Must** = seasonal-baseline z-score/standardized residual plus simple SPC rules (1 point >3σ, or 8 consecutive same-side points) applied to the deseasonalized series — fully implementable in DAX with a seasonal baseline measure and a sign/run-length counter; **Prefer (flag need for support)** = Chow test for a *specific, analyst-nominated* candidate date, since it's spreadsheet-feasible but needs a hypothesis a business user supplies, and a simplified/non-recursive CUSUM-style running deviation as a softer, non-parameter-tuned heuristic; **Avoid in self-service DAX / require a data scientist** = full tabular CUSUM with tuned k/h ARL targets, PELT, and Bayesian change-point detection (BOCPD), because each needs either genuine recursion, whole-series optimization, or posterior computation outside DAX's model.
- Because a detected signal (whether SPC rule violation, Chow F-stat significance, or a PELT/CUSUM breakpoint) is a *statistical* artifact of the chosen model and parameters, none of these methods identify *causation* — they only narrow *when* to look. This should be made an explicit guardrail in the skill: "a change point is an investigation trigger, not an explanation," paralleling the SPC literature's own "signal ≠ proof of cause" framing.

### Gaps
- No source directly addresses how reliable Chow/CUSUM/PELT/Bayesian methods are specifically for *count* data (vs. continuous, roughly-normal process data) at monthly granularity with n≈240 — most SPC/econometric sources assume continuous or rate data; count-specific caveats (e.g., variance scaling with volume, needing log or rate transforms first) were not found as explicit sourced guidance and are only inferable from general statistical practice, not cited here as confirmed fact.

## For outlier detection, what is the correct way to compute a seasonal-baseline standardized residual, and when does MAD outperform SD-based methods?

### Takeaway
The correct seasonal-baseline residual is: deviation = observed month − mean of the same calendar month across the prior N years (commonly 4–5 years), then standardized by dividing by the standard deviation of that same-month history (or, more robustly, the residual spread after removing trend/seasonality); MAD-based (median ± k×1.4826×MAD) scoring should replace or supplement the mean/SD version whenever the baseline itself may contain the outliers you're trying to detect, since MAD has a much higher breakdown point and is far less distorted by the extreme values it is evaluating.

### Cited Findings
- Official excess-mortality surveillance (a close real-world analog to "monthly count with known seasonality") computes a seasonal baseline as the mean of the same calendar period across the preceding years — the UK's weekly mortality surveillance uses a 5-year same-period mean, Germany uses 4 years, Belgium uses 11 — [arXiv, "Excess deaths, baselines, Z-scores, P-scores and peaks"](https://arxiv.org/pdf/2010.10320)
- A z-score in this framework is explicitly defined as "how many standard deviations above the baseline threshold" the observed count is, and the UK's weekly report flags a period when the observed count exceeds the upper 2-sigma threshold around the expected baseline — [GOV.UK, Weekly all-cause mortality surveillance](https://www.gov.uk/government/statistics/weekly-all-cause-mortality-surveillance-2025-to-2026/weekly-all-cause-mortality-surveillance-week-42-2025-report-up-to-week-38-2025-data); [EuroMOMO, What is a z-score?](https://euromomo.eu/how-it-works/what-is-a-z-score)
- EuroMOMO's z-scores are computed on a de-trended, de-seasonalized residual series (after a variance-stabilizing power transform), with the standard deviation drawn from the residuals around the fitted baseline — not from the raw same-month values directly — [EuroMOMO, What is a z-score?](https://euromomo.eu/how-it-works/what-is-a-z-score)
- Excess = observed − baseline; a P-score expresses that gap as a percentage of baseline, which is more comparable across differently-sized populations/programs than an absolute z-score — [arXiv, "Excess deaths..."](https://arxiv.org/pdf/2010.10320)
- Leys et al. (2013) argue the common "mean ± 3 SD" rule is problematic because both the mean and SD are themselves highly sensitive to the outliers being tested for, creating a circularity/masking problem — [arXiv summary citing Leys et al., via search synthesis](https://www.chromatographyonline.com/view/robust-statistics-median-vs-mean-standard-deviation-vs-mad-data-analysis)
- MAD-based detection uses median ± k×MAD (k≈3 is a common threshold per Leys et al.), where raw MAD is scaled by ≈1.4826 to be comparable to SD under normality (since the MAD of a standard normal is ≈0.6745, not 1) — [MathWorks, mad function documentation](https://www.mathworks.com/help/stats/mad.html)
- A demonstrated empirical example (50 normal draws plus one injected outlier of value 10): the SD-based ratio inflated to ~1.46 versus the clean baseline, mean-absolute-deviation ratio to ~1.18, while the median-based MAD ratio moved only to ~1.03 — i.e., MAD was least distorted by the single injected outlier — [MathWorks, mad function documentation](https://www.mathworks.com/help/stats/mad.html)
- Theoretical breakdown point: standard deviation has a 0% breakdown point (even one extreme value can arbitrarily inflate it), while median-based MAD can tolerate up to 50% contaminated/outlying observations before breaking down — [SimpleDecisionMaker, MAD calculator reference](https://simpledecisionmaker.onrender.com/tools/median-absolute-deviation-calculator/) (commercial/secondary source; verify against a stats textbook for the formal breakdown-point proof)
- The Iglewicz & Hoaglin modified z-score (using median and MAD rather than mean and SD) does not assume normality and is noted to be more robust than the traditional z-score, particularly in smaller samples — [MathWorks, mad function documentation](https://www.mathworks.com/help/stats/mad.html)
- General guidance: SD-based methods remain the default for roughly symmetric data without major outliers (because SD feeds directly into standard inferential statistics like t-tests/ANOVA/regression); MAD/median is the more defensible choice for skewed distributions, small samples, or data suspected to already contain outliers/errors — [search synthesis citing Leys et al. and related sources](https://www.chromatographyonline.com/view/robust-statistics-median-vs-mean-standard-deviation-vs-mad-data-analysis)

### Inferences
- For a BI skill on monthly program counts with a strong, recurring June–October peak, the "correct" seasonal-baseline residual should be: (a) compute same-calendar-month mean and SD/MAD across a rolling 4–5 year lookback (long enough to average out one-off noise, short enough to track genuine slow drift in the program), (b) standardize the current month's deviation against that same-month baseline, not against the whole year's distribution, and (c) prefer MAD over SD for the *baseline's own* spread calculation whenever the history window is short (a handful of years × one month = 4–5 data points) or suspected to contain its own anomalous prior-year months, since a single bad historical year can badly inflate an SD-based baseline and mask future real anomalies (masking effect). This is a synthesis across the mortality-surveillance methodology and the MAD-robustness literature, not a single directly-cited "do it this way for BI" source.
- With only 4–5 same-month data points to build a per-month baseline (a realistic constraint even with 240 months = 20 years of history, since only ~20 Junes, ~20 Julys, etc. exist), small-sample robustness matters more than in large-N settings — reinforcing MAD/median as the safer default for the baseline spread calculation specifically because of the Iglewicz & Hoaglin small-sample robustness finding above.

### Gaps
- No source directly specifies an ideal lookback window length (number of years) for a *monthly* program-count seasonal baseline outside the mortality-surveillance domain; the 4–5–11 year range found is specific to excess-mortality practice and was not validated for a general BI/operational-metrics context.
- No source gives a worked numeric example of the median ± 3×1.4826×MAD seasonal-baseline rule applied to monthly count data specifically (all MAD-robustness evidence found was for generic/non-seasonal distributions); applying it to a same-month lookback series is a reasonable extrapolation, not a directly cited practice.

## Which outlier method is most appropriate for monthly data with strong recurring seasonality, and why does naive global IQR misfire?

### Takeaway
For monthly counts with strong, predictable seasonality, the standard-good-practice recipe is to remove the seasonal pattern first (via STL decomposition or a same-month seasonal baseline) and only then apply a simple robust rule (IQR or MAD) to the *residual*; applying a global IQR directly to the raw seasonal series routinely misfires because the method has no concept of "which month this is" — it will flag every normal June–October peak month as an outlier (since they sit outside the whole-year quartile fences) while missing real anomalies inside the off-season.

### Cited Findings
- STL (Seasonal-Trend decomposition using Loess) is from Cleveland, Cleveland, McRae & Terpenning, "STL: A Seasonal-Trend Decomposition Procedure Based on Loess," *Journal of Official Statistics* 6, pp. 3–73, 1990 — [statsmodels STL documentation, citing Cleveland et al. 1990](https://www.statsmodels.org/dev/generated/statsmodels.tsa.seasonal.STL.html)
- The standard anomaly-detection recipe on seasonal data is: decompose with STL into trend + seasonal + remainder, then run a detector (adaptive thresholding, ESD, or simple z-score/IQR) on the remainder only — [Splunk, Time Series Decomposition documentation](https://docs.splunk.com/Documentation/DSP/1.0.1/FunctionReference/TimeSeriesDecomposition)
- The motivation: naive detectors on raw seasonal data mistake normal seasonal effects (e.g., quiet weekends, high-volume mid-week days) for anomalies; removing the seasonal component first avoids this — [Splunk, Time Series Decomposition documentation](https://docs.splunk.com/Documentation/DSP/1.0.1/FunctionReference/TimeSeriesDecomposition)
- The Twitter/AnomalyDetection research (arXiv 1704.07706) notes STL's residual tends toward a unimodal distribution well-suited to standard outlier tests (e.g., Extreme Studentized Deviate/ESD), and that STL's use of loess for the seasonal component (vs. classical decomposition) makes it more robust to extreme values corrupting the fitted seasonal pattern itself — [arXiv, "Automatic Anomaly Detection in the Cloud Via Statistical Learning"](https://arxiv.org/pdf/1704.07706)
- A limitation noted in 2025 research: standard STL can still absorb genuine collective anomalies into the fitted trend or seasonal components rather than leaving them in the residual, which can suppress detection of sustained anomalous periods — [arXiv, "Detection of collective and point anomalies at the presence of trend and seasonality"](https://arxiv.org/html/2508.21128v1)
- A practical alternative/approximation to full STL found in tooling practice: a rolling/windowed IQR sized to one or two full seasonal cycles (rather than a single global IQR across the whole series), paired with median/MAD instead of mean/SD when the distribution is skewed or heavy-tailed — [search synthesis of R `quickOutlier` and `timetk::anomalize` documentation](https://daniellop1.r-universe.dev/quickOutlier/doc/manual.html)
- One R package (`anomalize`-style tooling) implements exactly the "STL decompose, then IQR-fence the Remainder component at 3×IQR" pattern as a packaged workflow — [search synthesis, R `timetk`/`anomalize` package documentation](https://search.r-project.org/CRAN/refmans/timetk/html/anomalize.html)
- A research paper states plainly that a complex seasonal pattern in a series "could affect the properties of the usual outlier detection procedures," so seasonality must be modeled correctly before an outlier rule is applied — [search synthesis, via academic source on additive outliers in seasonal series](https://research.uniroma1.it/en/node/52840)
- Tukey's original IQR fence convention (Q1 − 1.5×IQR, Q3 + 1.5×IQR for "outside" points, 3×IQR for "far out" points) flags roughly 0.7% of values as outliers under a normal distribution — a property specific to IID, non-seasonal, roughly-normal data, which a raw seasonal monthly series does not resemble — [arXiv, "Unifying Boxplots: A Multiple Testing Perspective," 2025](https://arxiv.org/html/2510.20259v1)

### Inferences
- Full STL is the statistically "best" of the Part B methods for strongly seasonal monthly counts, but it is a Loess-based numerical procedure with no native DAX equivalent (it requires fitting local regressions iteratively across the series) — like PELT, this puts genuine STL outside self-service DAX and into "needs R/Python, or a pre-computed import" territory.
- A legitimate, DAX-buildable approximation that captures most of STL's benefit for a BI skill is the seasonal-baseline standardized residual described in the prior question (same-month multi-year mean/median, with MAD or SD as spread) — this is effectively a simplified single-season STL substitute that a business analyst can build and audit in Power BI, whereas global (non-seasonal) IQR across the whole series should be explicitly called out as a method to avoid for this data shape.
- Given the June–October peak pattern described in the brief, a global/whole-year IQR would almost certainly flag some or all of the 5 peak months as "outliers" every single year (a systematic false-positive, not a one-off error) while being under-sensitive to a genuine anomaly occurring in a normally-quiet month (because the off-season IQR band is being stretched wide by the inclusion of peak-month values in the same fence calculation). This is a direct logical inference from the cited mechanics of IQR and the stated seasonal pattern, not an independently sourced empirical test on this specific dataset.

### Gaps
- No source provided a quantified false-positive/false-negative rate comparing global IQR vs. seasonal-baseline/STL-residual methods specifically on monthly count data with a magnitude-5-month seasonal peak (the closest sourced evidence is qualitative, e.g., the KNIME example where plain IQR "fails to discover any outlier," which is a single anecdotal case, not a general benchmark).
- No source in this pass gave a DAX-native approximation of STL itself (as opposed to the simpler seasonal-baseline z-score); this reinforces that STL proper should be tiered as "needs specialist tooling," with the seasonal-baseline residual as the BI-native substitute.

## What's the standard caveat language used in official statistics / quality-control literature about NOT automatically treating a statistical outlier as an operational error or a real phenomenon?

### Takeaway
Official-statistics and quality literature consistently separates "outlier" (an extreme value, which may be real) from "error" (an actual mistake in how the data was generated or recorded), and explicitly warns that an outlier must be investigated, not auto-corrected or auto-explained — the same "signal to investigate, not proof of cause" language recurs independently in SPC (control-chart rule violations) and in official-statistics outlier-editing guidance.

### Cited Findings
- Eurostat defines an outlier as a value in the tail of the distribution and separately notes that outliers "are often regarded as more likely to be incorrect" than values in the main body — language that treats incorrectness as a *possibility to check*, not a default conclusion — [Eurostat, Statistics Explained outlier detection methods](https://ec.europa.eu/eurostat/statistics-explained/SEPDF/cache/3082.pdf)
- A US Census Bureau working paper (Coleman, 2002) distinguishes "extreme errors" (simply the largest *errors*) from "outliers" (large values that merely *indicate possible* problems with how the data were generated) — making clear an outlier is a symptom to check, not a confirmed error — [US Census Bureau, "Measures of Estimates Quality" (2002)](https://census.gov/library/working-papers/2002/econ/2002-coleman.html)
- Survey-statistics literature explicitly states that outliers identified during estimation "are often not erroneous at all," and that analysts must separately judge whether an extreme-but-genuine value should be downweighted, since doing so purely because it's extreme risks distorting the estimate in the other direction — [Springer, survey statistics review on outlier treatment](https://link.springer.com/doi/10.1007/s42081-020-00091-y)
- Data-quality guidance states directly that "observing outliers does not necessarily indicate a data error but a data property, which may be of substantial interest from a substant[ive] point of view" — [University of Greifswald, data quality guidance on outliers](https://dataquality.qihs.uni-greifswald.de/PDQC_DQ_3_2_1_1.html)
- Outlier-analysis guidance distinguishes "invalid outliers" (which represent real data errors and are the target of correction) from "valid outliers" (which arise from genuine random variation and are not errors and should not be "fixed") — [IDC/IDEA, Outlier Analysis guidance](https://www.ideadata.org/sites/default/files/media/documents/2020-01/IDC-OutlierAnalysisFINAL.pdf)
- In the SPC/quality-control tradition, a control-chart rule violation (Western Electric/Nelson rules) is explicitly framed as suggesting an "assignable cause" for investigation — not proof that one exists: "a rule violation suggests an assignable cause — it does not prove one exists" — [QualityGurus, Nelson Rules (and Western Electric Rules)](https://www.qualitygurus.com/nelson-rules-and-western-electric-rules-for-control-charts/)

### Inferences
- A governed BI skill should adopt a direct paraphrase of this convergent language as its standard caveat footer wherever an outlier/change-point flag is surfaced: *"This is a statistical signal that this period's value fell outside its expected range/pattern — it indicates something worth investigating, not a confirmed data error and not a confirmed real-world cause. Verify against source records and operational context before acting on it."* This synthesizes the Eurostat/Census/Springer/Greifswald/IDC "outlier ≠ error" framing with the SPC "signal ≠ proof of cause" framing, since both literatures converge on the same two-step discipline: (1) a flagged point is only a candidate for review, and (2) the reviewer must separately determine whether it reflects a data problem, a real operational event, or ordinary variation before treating it as either.

### Gaps
- No single source combines all five elements (outlier≠error, error≠outlier, valid-vs-invalid outlier, SPC signal≠proof, and a ready-made "caveat sentence" for dashboards) in one place — the caveat language recommended above is a synthesis across the cited sources, not a verbatim quotation from a single official standard; if the project needs a literally quotable standard, Eurostat's or the Census Bureau's own documents are the strongest primary sources to cite directly.
